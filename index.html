OS · Crash2025.09 ~ 2026.03

Android 16 WebView 콜드 스타트 크래시 대응

앱 코드 변경 없이 Android 16 단말에서만 급증한 크래시를 OS 리소스 매핑 결함으로 좁혔습니다. 착수 5일 만에 API 36(Android 16) 한정 방어 코드를 적용했고 이후 OS 수정과 함께 크래시율은 0.1% 미만이 됐습니다.

결함 리포트 제출. One UI 8.5부터 OS에서도 해소

문제

Android 16(One UI 8.0)으로 올린 단말에서 콜드 스타트 중 WebView 초기화 단계에 앱이 바로 종료됐습니다. 그 사이 앱 코드는 바뀐 게 없었는데 Play Console 크래시 지표가 평소 대비 약 150,000% 급등했습니다.

해결

크래시 로그마다 ResourcesImpl 리다이렉션이 반복됐고 같은 빌드가 OS 버전에 따라 다르게 동작했기 때문에 앱 로직보다 OS의 리소스 매핑을 먼저 의심했습니다. 베타 기간에 처음 잡은 증상은 Google Issue Tracker에 올리고 삼성에는 QA 이력과 dumpstate 로그를 보냈습니다. 삼성의 확인 결과는 플랫폼 리소스 매핑 결함이었습니다. GMS 업데이트로 바뀐 리소스 경로를 앱이 곧바로 반영하지 못하는 경합이 있었는데 Android 16에서 리소스 참조 위반 정책이 강해지면서 이 경합이 바로 종료로 이어졌습니다.

OS 수정 시점을 알 수 없어 앱에서 먼저 막았습니다. API 36 단말에서만 Application.onCreate에서 GMS 패키지 컨텍스트를 미리 불러 WebView가 리소스를 참조하기 전에 경로가 준비되게 했습니다. 분석 과정은 블로그에 정리해 두었습니다.

내 역할

증상 분석과 원인 가설부터 방어 코드 구현과 배포, Google·삼성 리포트까지 담당했습니다.

문제

Play Console의 과도하게 정지된 프레임(한 프레임 700ms 이상) 비율이 건설사 앱 한 곳에서만 올라갔습니다. 같은 네이티브 코드를 쓰는 다른 건설사 앱은 변화가 없었습니다.

해결

두 앱이 다른 건 웹 콘텐츠였습니다. 같은 에뮬레이터에서 같은 스와이프로 두 앱을 비교하고 dumpsys gfxinfo framestats로 프레임을 모은 뒤 Perfetto와 Chrome DevTools Protocol 트레이스로 구간을 나눴습니다. 앱 UI 스레드 구간은 0.6~3.6ms였습니다. 지연은 WebView가 웹 화면을 그리는 GPU 래스터·컴포지팅 구간에서 나왔고 영향 세션은 Exynos 계열 중저가 기기 2종에 몰려 있었습니다.

원인이 웹 쪽이라 수정은 웹팀 몫이었습니다. throttle 없이 도는 스크롤 위치 저장, HTML로 직접 만든 당겨서 새로고침, will-change 애니메이션 세 곳은 사내 발표에서 의심 지점으로 공유했습니다. 웹팀은 이를 포함해 6개 항목을 고친 브랜치를 같은 조건으로 다시 쟀습니다. 100~700ms 롱태스크도 1,683건에서 110~145건으로 줄었습니다.

내 역할

이상 감지부터 대조 실험 설계, 계측과 원인 구간 특정, 리포트와 발표까지 맡았고 웹 코드 수정은 웹팀이 했습니다.

측정값은 소프트웨어 GPU 에뮬레이터 기준입니다. 측정 뒤 일부 변경이 코드리뷰에서 철회돼 배포된 코드와 차이가 있고 실기기 검증과 이후 Vitals 추이 확인이 남아 있습니다.

인증 저장소 전환

자동 로그아웃 문의 49건과 계정 제한 장애를 계기로 시스템 계정 의존을 없앴습니다.

이틀, 2회
문의 49건 이후 Android 핫픽스 배포
10일
계정 장애 접수부터 저장소 전환 개발 완료까지 (상용 반영 17일)

문제

로그인 상태는 Android AccountManager의 시스템 계정과 DataStore 토큰을 함께 보고 판정했습니다. 2025년 4월 말 이틀 동안 자동 로그아웃 관련 문의가 49건 모였습니다(앱 접속 오류 30, 재로그인 실패 16, 승인 팝업 재노출 3). 같은 시기 코드에서는 두 경로가 확인됐습니다. 시스템 계정 변경 이벤트와 앱 내부 제거 이벤트가 겹쳐 로그아웃이 두 번 실행되는 경로, 그리고 웹 로그인 뒤 토큰이 늦게 도착하는 동안 "계정은 있는데 토큰이 없는" 상태를 로그아웃으로 판정하는 경로입니다.

해결

이틀 동안 저버전 OS 오류 보완과 로그인 풀림 수정 핫픽스를 한 번씩 배포했습니다. 웹에 토큰 일부가 남은 것으로 보이는 문제는 웹팀이 방어 코드를 넣어 정리했습니다.

2026년 2월에는 한 사용자가 출입 기능 설정 직후 단지 정보 확인 팝업에 계속 막혔습니다. AOSP의 AccountManagerService를 보면 기기 계정이 100개를 넘을 때 계정 추가가 경고 로그만 남기고 실패합니다. 계정 생성이 시스템에서 거부됐을 가능성을 가설로 두고 계정 추가 실패 시 재시도와 오류 코드를 넣은 보완판을 사흘 뒤 배포했고 이 버전에서 증상이 사라졌습니다.

두 장애 모두 시스템 계정에 기대는 구조에서 나왔습니다. 커스텀 Authenticator 서비스와 계정 이벤트 리스너를 걷어내고 토큰을 EncryptedSharedPreferences 기반 저장소로 옮겼습니다. 기존 토큰은 DataStore 사본에서 한 번만 이전하며 실패하면 다음 실행 때 다시 시도합니다.

내 역할

장애 담당자로서 증상 분리, Android 수정과 배포, 장애 보고서를 맡았습니다. 문의 취합은 운영팀, 접속 오류 집계와 패치 방침은 팀 리드, 웹 토큰 정리는 웹 개발자 담당이었습니다.

Application에 몰린 초기화 5개는 androidx.startup Initializer로 나누고 위젯 ON 표시는 실제 서비스 상태와 맞췄습니다. 토큰 갱신은 인터셉터 한 경로에서 single-flight로 직렬화하고 rotation 때 오래된 토큰을 채택하지 않는 규칙은 테스트로 고정해 두었습니다. 끝으로 앱스킴, App Links, 푸시, 위젯, 숏컷, 커뮤니티 6가지 진입 경로를 라우터 하나로 모았습니다. 이제 실행 중인 앱에 다시 들어와도 스플래시가 뜨지 않습니다.

Figma Variables를 원본으로 Compose 테마를 다시 짜고 건설사별로 갈라져 있던 레거시 테마 33개 파일(6,840줄)을 지웠습니다.

문제

레거시 테마는 건설사별 패키지마다 Color, Theme, Typography 파일 3개를 따로 두는 구조라 디자인을 바꾸면 브랜드 수만큼 같은 수정을 반복해야 했습니다.

해결

디자이너가 관리하는 Figma Variables를 tokens.json으로 저장소에 들여와 원본으로 삼았습니다. Primitive에는 컬러 스케일 21종과 간격·반경·투명도를 둡니다. Semantic에는 배경·텍스트·아이콘·테두리 등 역할 토큰 106개를 두어 브랜드별 light/dark 값을 만듭니다. Component 계층은 따로 파일을 두지 않고 버튼 같은 컴포넌트 안에서 Variant와 Size를 Semantic 토큰에 연결합니다.

토큰은 staticCompositionLocalOf로 내려줍니다. 기본값을 error로 두어 테마 밖에서 토큰을 읽으면 즉시 실패합니다. 첫 버전 이틀 뒤에는 테마 함수의 브랜드·모드 기본값도 없애 호출하는 쪽이 항상 명시하도록 바꿨습니다. 토큰 코드는 생성기 없이 직접 썼고 원본과 코드가 어긋나는지는 신규 브랜드 추가 스크립트가 확인합니다.

Glance 위젯에서는 CompositionLocal을 쓸 수 없어 Primitive 스케일은 그대로 공유하고 Semantic 토큰만 ColorProvider(day, night) 쌍으로 다시 정의했습니다. 다크모드는 웹이 WebBridge로 저장한 테마 값을 StateFlow로 받아 반영합니다.

내 역할

토큰 계층을 설계하고 Compose 테마·위젯 전환까지 직접 했습니다. Figma Variables는 디자이너가 관리했습니다.

문제

AI 리뷰와 AI 수정을 주고받게 했더니 작업과 관계없는 파일이 바뀌고 요청하지 않은 리팩터링이 들어가고 기획에서 정한 로직까지 바뀐 PR이 나왔습니다. 머지 전 마지막 diff 확인에서 잡았고 수정 범위를 정해 주지 않은 것이 원인이었습니다.

해결

레포에는 팀이 같이 쓰는 규칙을 두었습니다. 루트 CLAUDE.md는 어디서 무엇을 찾는지와 절대 규칙만 두는 라우터로 줄이고 상세 규칙은 docs 문서와 모듈별 CLAUDE.md 4개로 나눴습니다. docs/_index.json에는 작업 영역별로 읽을 문서(triggers), 모듈별 문서(moduleScopes), 코드를 바꾸면 함께 고칠 문서(syncMatrix)를 적어 AI가 필요한 문서만 읽게 했습니다. AGENTS.md를 CLAUDE.md에 연결해 두어 Codex 같은 다른 도구도 같은 규칙을 읽습니다.

작업 절차는 6단계입니다. 요청을 받아도 바로 코딩하지 않습니다. 의존성 지도에서 영향 범위를 뽑고 변경 파일과 영향 범위를 보고해 승인을 받은 뒤에만 고칩니다. 자동 커밋과 push, 문서 자동 갱신은 금지했습니다.

개인 작업에는 티켓마다 worktree를 따로 만들고 커밋부터 셀프 리뷰, PR 생성, PR 리뷰, 리뷰 반영까지를 스킬로 이었습니다. 셀프 리뷰는 PreToolUse 훅으로 git push 앞에 걸려 있어 리뷰를 거치지 않은 브랜치는 push되지 않습니다. AI 리뷰는 지적까지만 하고 반영 여부와 최종 판단은 직접 합니다. 여러 작업은 Orca 워크스페이스와 worktree로 병렬로 돌리고 새 worktree에 빌드용 설정 파일을 복사하는 스크립트도 두었습니다.

내 역할

레포 하네스와 개인 파이프라인은 직접 만들었습니다. PR에 붙는 CI 봇 리뷰는 팀원이 만든 조직 공통 워크플로를 씁니다.

도메인별 에이전트 4종은 만들어 두고 거의 쓰지 않았고(10개월 9회), 라우터로 시작한 CLAUDE.md는 20KB까지 불어났습니다. CLAUDE.md를 다시 줄이는 일과 빌드·테스트 통과를 push 게이트에 넣는 일이 다음 과제로 남아 있습니다.
