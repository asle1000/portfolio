02OS · Crash · 2025.09 ~ 2026.03

Android 16 WebView 콜드 스타트 크래시, 착수 5일 만에 방어

상황
Android 16으로 올린 단말에서 콜드 스타트 중 WebView 초기화 단계에 앱이 바로 종료됐습니다. 앱 코드는 바뀐 게 없었는데 Play Console 크래시 지표가 평소 대비 약 150,000% 급등했습니다.
판단
크래시 로그마다 ResourcesImpl이 반복되고 같은 빌드가 OS 버전에 따라 다르게 동작해, 앱 로직보다 OS의 리소스 매핑을 먼저 의심했습니다. GMS 업데이트로 바뀐 리소스 경로를 WebView가 곧바로 반영하지 못하는 경합이 Android 16의 강화된 정책에서 종료로 이어진 것이었습니다. OS 수정 시점을 알 수 없어 API 36 단말에서만 GMS 패키지 컨텍스트를 미리 불러 경로를 준비하는 방어 코드를 넣고, Google Issue Tracker와 제조사 리포트를 병행했습니다.
0.1% 미만방어 코드 배포 후 크래시율(Play Console)
5일방어 코드 착수부터 적용까지

맡은 범위 증상 분석과 원인 가설부터 방어 코드 구현·배포, 리포트까지 맡았습니다. 블로그: Android 15~16 WebView Cold Start 크래시 분석

03BLE · Geofence · 2024.05 ~ 07

BLE 출입 배터리 소모 18.9% → 1.3%

상황
바이비패스는 스마트폰만 들고 지나가면 공동현관과 엘리베이터가 반응하는 출입 기능으로 하루 17~20만 건을 처리합니다. 초기 구현은 WakeLock으로 BLE 스캔을 계속 유지해 Doze 절전 정책과 충돌했고, 배터리 소모가 18.9%였습니다(Battery Historian, 실기기 7대).
판단
스캔이 필요한 곳은 집 근처뿐이라고 보고, 거주 단지 반경을 Geofence로 등록해 반경 안에서만 스캔과 포그라운드 서비스를 실행했습니다. 스캔 주기 조정도 함께 적용했습니다. 일부 단지에 먼저 적용한 뒤 전 단지로 넓혔고, 현장 문제를 재현 없이 보려고 로그 업로드와 주변 모듈 정보 첨부를 하는 원격 진단도 넣었습니다.
18.9% → 1.3%배터리 소모(지오펜스와 스캔 주기 조정 합산)
0.3% 이하BLE 오류율, 전환 뒤에도 유지
2주 → 1~2일현장 이슈 대응(접수부터 분석·안내까지)

맡은 범위 지오펜스 조건부 스캔 설계와 구현, 단계 적용, 진단 기능을 맡았습니다. 기준 좌표와 반경은 서버의 단지 데이터를 씁니다.

04NFC · HCE · 2024 ~ 2025

HCE 미지원 단말과 리더 없는 단지까지 앱카드 확장

상황
하루 8천 건 쓰이는 HCE 앱카드에서 카드 발급사마다 다른 AID가 충돌해 인식이 불안정했고, 홍미·샤오미 같은 일부 단말은 HCE를 지원하지 않았습니다. HCE 리더 모듈이 없는 단지도 NFC 태그만 붙여 출입하게 해 달라는 영업 요청도 들어왔습니다.
판단
AID 충돌 조건을 나눠 우선순위 규칙을 바꾸고 처리 경로를 둘로 나눴습니다. HCE를 쓸 수 있는 단말과 단지는 HCE로, 그렇지 않으면 NFC 태그 읽기로 처리하며 iOS의 태그 읽기 방식과도 맞췄습니다. 읽기 모드는 별도 화면 대신 한 화면에서 전환하게 하고, 단지가 지원하는 모드에 따라 노출을 제어했습니다.
약 3주태그 읽기 모드 요청부터 알파 배포까지
하루 8천 건앱카드 이용(GA4)

맡은 범위 AID 우선순위 규칙, 단말 이원화, 읽기 모드 구현과 배포를 맡았습니다.

05HCE · SDK · 2020 ~ 2022

HCE 교통카드 SDK 초도 버전 안정화

상황

판단
지역별 실제 단말로 RF 튜닝과 현장 테스트를 반복하며 금액 오류의 원인을 찾아 고쳤습니다. AsyncTask 기반 비동기 처리는 Coroutine으로 옮겨 안정성을 확보했습니다.

7곳 이상금융·교통·공공 상용 배포

맡은 범위 Android SDK 초도 버전 안정화, 지역별 현장 테스트, iOS SDK 포팅을 맡았습니다.
